Security Information

A transparent overview of security controls in this project. This is a student demonstration — see limitations below.

⚠ Development Notice: This application uses a self-signed TLS certificate. Browsers will display a trust warning. This is expected for local development and does NOT indicate the same guarantees as a CA-issued certificate.

🔒 TLS / HTTPS Encryption

Implemented

  • Flask serves traffic over TLS on https://127.0.0.1:5000
  • HTTP listener on port 5001 issues a 302 redirect to HTTPS — path is preserved
  • Redirect target is always the fixed local origin — no open-redirect vulnerability
  • HSTS header sent on HTTPS responses (max-age=31536000; includeSubDomains)

Development Limitations

  • Certificate is self-signed (not CA-issued) — browser shows trust warning
  • TLS hides application data, not connection metadata (IP, timing)
  • HSTS is only effective after the user accepts the self-signed cert in the browser

🔑 Authentication & Password Security

Implemented

  • Werkzeug generate_password_hash — PBKDF2-SHA256 or Scrypt, never plaintext
  • Login uses check_password_hash (timing-safe comparison)
  • Generic "Invalid username or password" message — prevents username enumeration
  • session.clear() called before login — prevents session-fixation attack
  • Logout uses POST + CSRF token; session fully cleared on sign-out
  • Server-side validation: length, character set, password match

Out of Scope

  • Rate-limiting and brute-force lockout (not implemented)
  • Multi-factor authentication (MFA)
  • Password reset / forgot-password flow
  • Account lockout after repeated failures

🛡️ CSRF Protection

Implemented

  • Flask-WTF CSRFProtect applied to all POST forms (register, login, logout)
  • Tokens are time-limited (1 hour) and validated server-side on every submission
  • Expired or invalid tokens produce a user-friendly flash message and safe redirect
  • Logout route is POST-only — prevents CSRF-driven forced logout via GET link

🗄️ Database Security

Implemented

  • All SQL queries use parameterized statements — SQL injection prevented by design
  • Only id, username, password_hash, and created_at are stored
  • No default admin account or test credentials seeded in the database
  • SQLite WAL mode and foreign-key enforcement enabled
ℹ Disclaimer: This application is a student learning project demonstrating key web-security concepts. It is not production-ready. Missing controls include rate-limiting, account lockout, CA-signed TLS, and a formal security audit.
